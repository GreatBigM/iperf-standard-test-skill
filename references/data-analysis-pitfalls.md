# iperf3 数据分析坑（data-analysis-pitfalls）

> 遇问题按需查。全部为实测验证的教训（2026-08，嵌入式 WiFi 设备系列）。

## 1. 单轮测量不可信（最高频坑）

- **症状**：某改动后单轮吞吐下降 5-10%，误判为回归
- **实测案例**：WiFi 信号直读移植后首测 107.7M vs 基线 112M（-6.6M），补测 112/113/112M 与基线持平——纯环境波动
- **铁律**：3 轮取均值；下降时补验证轮（同时段交替测）；单轮结论不可信

## 2. 跨时段对比天然不可靠

- **实测**：同一设备 Case1 白天 121M → 深夜 52.6M（-57%），AP 状态昼夜差异巨大
- **判据**：>30min 的两次测试对比无意义；消融/回归必须同时段交替测
- 深夜 AP 差 + 环境干扰 → 相对关系都可能反转（深夜 Case3 > Case1 与白天相反）

## 3. 重传率是环境信号不是驱动信号

- **症状**：吞吐下降 + 重传升高（如 57 → 237/134）
- **解释**：重传高 = 无线环境差（AP 干扰/信道占用），不是驱动问题
- **判定**：对比轮次间重传差异判断环境波动；重传持平 + 吞吐下降 = 真回归

## 4. 爬坡误判

- **正确特征**：首秒吞吐 ≥80% 均值 = 无爬坡（TCP 窗口已到位）
- **爬坡特征**：首秒 20-40M 持续爬升到峰值 = BDP/窗口不足（检查 tcp_rmem/wmem 参数）
- **实测**：rmem/wmem 512K 后首秒即满速（111M），无爬坡；参数不足时前 3-5s 缓升
- 注意：前 1-2 秒的慢启动快升（111→123M）是正常 TCP 行为，不是爬坡

## 5. UDP 丢包 ≠ 掉线

- **设计内背压**：RX 高限速丢包是协议特性（UDP 无重传），TCP 同链路正常 + wpa COMPLETED = 链路干净
- **判据**：UDP 丢包 + TCP 正常 + wpa 全程 COMPLETED = 背压；wpa 掉线 = 真问题
- **红线**：可降速不可断联——掉线（wpa_state 非 COMPLETED）零容忍，吞吐可降

## 6. 多流掩盖单核瓶颈

- **实测**：单流 P1 反映单核 CPU 真实能力；多流 P5 CPU 分摊 → 每流劣化
- **判据**：驱动优化看 P1；系统负载看 P5
- TCP 512K 窗口优化单流 +16%，5 流仅 +2%（CPU 瓶颈摊薄窗口红利）

## 7. 数据提取陷阱

- `grep "SUM"` 拿汇总行（吞吐+重传+丢包）——**单流 P1 无 [SUM] 前缀**（用 `[  5]` 且内部带空格），须按行尾 sender/receiver 或正则匹配；用列索引会因 `[  5]` 内部空格导致列偏移（08-12 实锤，已改正则）
- `iperf3: error - the server is busy` = 重试信号不是失败（server 被占）
- 设备 busybox 无 head/nohup：`head` 用 `cat|grep` 替代；串口 `&` 不需要 nohup
- iperf3 死链接：`/system/bin/iperf3` 可能指向未挂载 SD 卡 → 显式用 `/tmp/iperf3`

## 8. 长测 vs 短测不可直接对比

- 300s 长测天然低于 60s 短测（长时间高负载 AP 降速/重传累积）
- 不要拿长测吞吐 vs 短测基线断言变慢；长测只看稳定性（Done + wpa 采样）

## 9. 丢包误归因到驱动（分层缺失）

- **症状**：UDP RX 丢包 26%，直接怪驱动
- **实测**：rxq_drop/deliver_drop 恒 0（驱动从不丢），丢在协议栈 udp_rcv CPU 饱和（UDP InErrors 高）——3.10 无 UDP GRO，逐包处理 52μs 上限
- **判据**：分层计数（驱动 /proc/net/dev + 协议栈 /proc/net/snmp）缺一不可；单看一边必误判

## 10. 吞吐骤降先查池状态

- **症状**：稳定跑着突然 45M→28M 崩
- **实测**：单帧模式池耗尽（emergency alloc 9→1 循环，上限 2100）——任务处理跟不上 → rxq 积压 → 池枯竭
- **判据**：`dmesg | grep -c "emergency alloc"` 非零 + 增长 = 池压力；此时不是无线问题也不是驱动 bug，是资源裕量不足

## 11. 32 位计数器回绕

- **症状**：单点读数偏低、或同一臂两轮差值变小/变负
- **根因**：`/proc/net/dev`、`netstat -s` 的计数是 **32 位**，单臂累计过 4GiB 即回绕
- **判据**：`delta = b-a if b>=a else b-a+2**32`；同时给 ratio 加上界（≤1.5）兜底，否则清零/重载会被“校正”成假高值；某段差值恒 0 先查是不是把前值读在了流量之后

## 12. dmesg 计数基线不是 0

- **症状**：拿 `dmesg | grep -c` 当故障数，两臂差几十条不可解释
- **根因**：业务态启动期本就自 dump（ISP 等 Call Trace）；环形缓冲翻页后计数只是“窗口内”而非“开机以来”
- **判据**：拆两类——`dmesg_fatal`（`Oops|panic|BUG:|rcu_preempt|soft lockup`，基线 0）与 `dmesg_err`（含 Call Trace，仅参考）；两臂对比前各自取基线，不可跨时刻比绝对值
